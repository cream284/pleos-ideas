결론: 우리 팀의 기획에 바뀌는 전제시간대별 핵심 발언추가 확인이 필요한 발표 내용공개 SDK와 아이디어 설계의 안전선현재 후보의 우선순위 재판정이번 주 실행 계획 (3인)제출 체크리스트원본과 검토 근거발언의 해석 범위

결론: 우리 팀의 기획에 바뀌는 전제

  1. 외부 API 사용과 공용 인터넷 연결은 가능하다. 운영진이 기술 Q&A에서 직접 답했다(49:06). 따라서 장소·시설·예약·제휴 서비스와 연동하는 B2B/B2C 구상은 공모전 개발 범위 안에서 검토할 수 있다.
  2. 실차 시연은 지원하지 않으며 Pleos Connect Emulator로 검증한다(32:24, 44:57). 차량 하드웨어나 실차 전용 센서를 전제로 한 기능은 제출 핵심으로 삼으면 안 된다.
  3. 공개 SDK 5종은 개발 단계에서 별도 승인 없이 권한 선언으로 사용할 수 있다고 안내했다(49:33). Vehicle, NaviHelper, STT, TTS, Fused Location이다. 앱마켓 실제 배포 단계의 권한 심사는 별도다.
  4. SDK 개수 자체보다 핵심 경험에 대한 적절한 활용이 중요하다. 고객 문제의 핵심 흐름에 필요한 SDK를 고르고, 그 연결을 시연으로 보이는 것이 중요하다고 명확히 말했다(43:20).
  5. 1차에도 작동 산출물은 가산점이고, 2차 PT에서는 실제 동작 앱이 필수다(18:32, 46:54). 따라서 11월 15일에는 한 가지 차량 특화 경험을 확실히 구현한 APK·GitHub·짧은 시연 영상을 내는 전략이 유리하다.

시간대별 핵심 발언

영상 시각 내용 기획·제출에 주는 의미
13:06–15:35 공모전은 운전자·탑승자를 위한 차량용 앱 구현. 앱이 완성되지 않아도 기획서 접수 가능. 스마트폰 동반앱이 아니라 차량 디스플레이의 주 사용 흐름을 설계한다.
15:41–16:07 아이디어 출발점은 사람의 불편·욕구. 차량 환경과 이동 맥락에서 풀고 SDK/API를 핵심 기능에 연결하라고 안내. 문제 장면 → 차량 신호/위치/음성 → 차량 안의 결정·행동이라는 한 줄을 제안서 첫 장에 둔다.
18:37–21:30 1차: 기획서·전원 서약서 필수, 프로토타입 영상·GitHub/APK 선택 가산점. 2차 PT 전 앱 완성·현장 시연. 발표용 목업보다 Emulator로 검증되는 핵심 기능 1개를 먼저 만든다.
23:37–24:31 심사: 차량 특화성, 창의성, 기술 활용성, 사업성. 가중치는 공개되지 않음. 네 항목을 같은 분량으로 쓰기보다, 각 항목별 증거를 하나씩 준비한다.
32:24–32:56 실차 시연은 지원하지 않음. 공식 Emulator에서 검증. UWB·직접 결제·실차 센서 등 비공개/미확인 기능은 미래 확장으로 분리한다.
34:17–37:12 Pleos Connect는 AAOS 기반 차량 인포테인먼트 플랫폼. 일반 모바일 앱을 차량 화면으로 옮기지 말고 차량이어서 유용한 앱을 만들라고 강조. ‘운전 중/정차 중/동승자/차량 상태’가 없으면 성립하지 않는 화면과 정책을 만든다.
40:50–43:29 Vehicle: 도어·주행·배터리/충전·공조 등. NaviHelper: 목적지·경유지·경로·정보 조회. STT/TTS/Fused Location 소개. SDK를 많이 쓰는 것이 목적은 아니라고 재강조. Vehicle+NaviHelper의 상태 전환을 주축으로, STT/TTS는 안전한 음성 상호작용, Fused Location은 장소 맥락에 제한해 쓴다.
44:57–46:53 Emulator와 Virtual Console로 기어·도어·배터리/충전 상태 같은 이벤트를 바꾸며 앱 반응을 검증 가능. 데모는 ‘Virtual Console 값 변경 → 앱의 안내/경로/음성 변화’를 한 컷으로 보여준다.
48:43–50:04 외부 API 사용 가능, 공용 네트워크 연결 가능. 개발 단계에는 SDK 권한 승인 절차 불필요. 호텔·시설·예약·결제 제휴, 기업 업무 시스템 등 외부 서비스 연동 가설을 PoC에 넣을 수 있다. 단, 계정/결제의 실제 상용 연동은 모의 응답과 범위를 분리한다.
51:24–52:51 제출·가산점·차량 UX·SDK와 핵심 기능의 연결을 마지막으로 재강조. 제안서와 시연 영상의 메시지를 하나로 맞춘다.

추가 확인이 필요한 발표 내용

37:07–37:30 부근에는 미공개 SDK 제공 계획으로 들리는 발언이 있다. 자동 전사만으로 정확한 범위를 확정하기 어려우므로, 공개 SDK 5종 외 기능이 이미 사용 가능하다는 근거로 해석하지 않는다. 추가 SDK 목록·제공 시기·Emulator 지원은 공식 공지로 확인한다.

공개 SDK와 아이디어 설계의 안전선

SDK / 환경 이번 설명회에서 확인된 활용 우리 기획에 적용할 방식 피해야 할 주장
Vehicle SDK 차량 상태, 주행, 배터리·충전, 공조; 일부 차량 기능 제어는 권한 범위에 따름 배터리/충전 상태와 현장 도착 준비·EV 업무 동선 연결 모든 차량 제어가 가능하다고 단정
NaviHelper SDK 목적지·경유지·경로 요청·내비 정보 조회 방문지 확정 → 차량 내비 목적지 설정 → 도착 단계 전환 자체 내비 전체를 구현한다는 전제
Fused Location SDK 차량 위치 기반 서비스 도착 반경·현장/시설 컨텍스트 전환 UWB급 정밀 위치 또는 승객 위치 추적
STT / TTS 음성 입력·음성 출력 운전 중 짧은 확인·안내, 정차 시 상세 선택 주행 중 긴 대화·복잡한 화면 조작
Emulator / Virtual Console 앱 실행, SDK 연동, 차량 상태 이벤트 가상 변경 핵심 상태 변화의 재현 가능한 데모 실차 검증·실제 센서 성능을 입증했다는 표현
외부 API / 공용 네트워크 사용 가능 시설·예약·B2B 운영 시스템 연동, 서버 기반 구독 서비스 제3자 결제·개인정보 연동이 이미 승인됐다고 표현

현재 후보의 우선순위 재판정

1. 현장 도착 보장 도우미 — 유지하되 이름과 약속을 조정

  • 권장 명칭: 현장 도착 준비 도우미
  • 강점: Vehicle(배터리/충전 상태) + NaviHelper(목적지/경로) + Fused Location(도착 맥락) + STT/TTS(짧은 안내)로 완결된 흐름을 만들 수 있다. 외부 API 허용으로 현장 작업·예약·고객 안내 연동도 가능하다.
  • 수정: 교통·현장 변수를 통제할 수 없으므로 ‘도착 보장’ 대신 도착 전 준비 누락을 줄인다로 문제를 정의한다.
  • Emulator 데모: 충전량 저하 또는 출발 지연 상태 변경 → 재계산/대안 경로 → TTS 확인 → 방문처 준비 메시지(모의 외부 API).

2. 도착을 준비하는 차 2.0 — 조건부 유지

  • 강점: 도착 반경과 차량 내비 흐름을 써서 호텔·리조트·오피스가 손님을 맞이할 시간을 만든다는 감성·사업성 메시지가 좋다.
  • 핵심 위험: UWB 정밀 위치, 자동 결제, 시설 제어를 현재 공개 SDK 기능처럼 말하면 안 된다.
  • Emulator 데모: NaviHelper 목적지와 Fused Location 기반 도착 임박 → TTS로 수신 동의 → 외부 API에 ‘예상 도착’ 전송 → 시설 준비 상태를 차량 화면에 표시.

3. EV 출장·현장업무 에너지 플래너 — 구현 우선 후보

  • 강점: 안내에서 직접 예시로 든 ‘배터리 상태와 이동 경로 결합’과 가장 가깝다. 차량 특화성과 구현 가능성이 선명하다.
  • 차별화 조건: 단순 충전소 추천이 아니라 현장 업무 약속을 지키기 위한 에너지 의사결정으로 좁힌다. 기업 구독은 방문 일정·차량 운영 현황 대시보드로 확장한다.
  • Emulator 데모: Virtual Console의 충전 상태 변경 → 방문 일정 유지 가능성 판단 → 충전 경유지 제안 → NaviHelper 경유지 설정 → TTS 안내.

발언의 해석 범위

이 영상은 공모전 개발·평가 방향의 공식 설명이다. 다만 Vehicle SDK의 개별 도메인, 권한, 앱마켓 배포 심사는 문서와 실제 프로젝트 설정을 다시 확인해야 한다. ‘외부 API/공용 네트워크 가능’은 해당 연결 자체의 허용을 뜻하며, 결제 사업자·개인정보·시설 제어 권한까지 자동 승인한다는 뜻은 아니다.
